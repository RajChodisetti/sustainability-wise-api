# Field finance capture and ledger ownership

The Field portal previously offered optional Hours input and a manual Mark invoiced toggle in `CostLinesPanel`. Both requests contradict the current dedicated API: `installHubFinanceService.ts` rejects non-null `hours` during creation, and any `hours` or `invoiced` property during update. Invoice reservation/issue/void lifecycle controls expense invoice state. This was a portal/API mismatch also mirrored by the mobile UI, not a reason to bypass audited financial settings or invoice ownership.

App-active time is internal evidence, not a source of billing/cost hours or invoice quantities (`CONTRACTS.md`, Scheduler internal active-time evidence). The current shared service computes `billableHours` and `costHours` from their separately audited overrides, defaulting each to zero, while retaining `actualHours` separately (`schedulerFinanceService.ts:2220–2229`). The Field adapter displays `labour.hours = shared.time.costHours` and maps each expense's legacy `hours` to null (`installHubFinanceService.ts:294,363`). Its create rejection text still mentions an active-work ledger, but that message is not the source of authority for displayed financial hours. The portal therefore describes audited financial settings without implying that app-active time drives charges.

The portal cost panel now shows returned hours and invoice flags read-only. Its new-cost request carries category, trimmed description, cost, optional sell amount and billable=true; it sends neither ledger-owned property. Category and amount validation, valid manual cost creation/deletion, automatic-line deletion protection, server errors, successful input clearing and failed-request draft preservation remain unchanged. Pricing and invoice workflows are unchanged. Existing API request/response compatibility types and routes are retained.

Five focused tests execute the production component's rendered controls and actual submit/delete handlers with controlled hooks. Three fail against the previous component; all five pass after this change. Coverage includes read-only ledger values, exact outgoing cost fields and installation scope, manual versus system deletion, read-only access, and request-error retention. Local tests do not establish a deployed portal fix or physical iOS mutation success. The corresponding native correction is tracked separately in the mobile repository's `docs/ios-web-parity-finance-ledgers.md`.

No active-work, invoice, expense or user records were changed by these tests. No server/database/auth contract, migration, dependency, shared component or other product was modified.
