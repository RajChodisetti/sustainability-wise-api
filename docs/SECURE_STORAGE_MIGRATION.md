# Secure Files, Storage Isolation, and Bootstrap Migration

This runbook covers Eco Audit Pro, Solar Sense, and InstallHub. It is designed
for an expand/backfill/contract rollout: every data move is copy-first,
checksum-verified, reversible, and leaves the legacy source intact until an
operator separately approves retirement.

## Resulting security boundaries

```text
PostgreSQL
├── ea_*  Eco Audit users and records
├── ss_*  Solar Sense users and records
├── ih_*  InstallHub users and records
└── shared registries
    ├── refresh_tokens.app
    ├── photo_registry.app
    ├── photo_copy_references.app
    ├── record_versions.app
    └── pdf_jobs.app

Object storage
├── Eco Audit bucket/root      dedicated IAM credential
├── Solar Sense bucket/root    dedicated IAM credential
└── InstallHub bucket/root     dedicated IAM credential
```

The three user tables are independent. A user or administrator in one table
does not become a user in another app. They currently live in one PostgreSQL
database/schema, so database-operator access remains a shared infrastructure
boundary. Object storage is physically separated by destination and credential;
the application prefix remains defense in depth, not the primary boundary.

All `/v1/files/*` reads now require either:

- a valid app-scoped bearer token plus parent/owner/assignee authorization; or
- a short-lived HMAC capability generated by the API for a completed export.

Raw upload `PUT` URLs are short-lived HMAC capabilities bound to app, upload
session, and expiry. Query strings are stripped from API request logs. A random
session ID by itself is not authorization.

Derived thumbnails use `<app>/_thumbnails/v2/...`. The old global
`_thumbnails/v1` cache is not moved because it is disposable; v2 previews are
regenerated lazily from an authorized original. Do not delete the old cache
until the client rollout and retention window are complete.

## Required secrets and destinations

Use independent random values for:

- `JWT_SECRET`
- `JWT_REFRESH_SECRET`
- `UPLOAD_CAPABILITY_SECRET`
- `FILE_CAPABILITY_SECRET`

Configure all three app destinations before selecting `dual` or `isolated`.
For Spaces/S3, each app must have a distinct bucket and a credential whose IAM
policy grants access only to that bucket. The API rejects duplicate configured
buckets, local roots, or IAM access-key identities, including accidental reuse
of the legacy destination. In production, `dual` and `isolated` modes reject
per-app local destinations; local roots remain available for development and
non-production migration tests. Bucket-policy scope still must be verified in
the storage provider because the API cannot introspect IAM permissions. See
`.env.production.example` for the complete variable set.

## Rollout

### 0. Capture recovery points

1. Take a PostgreSQL snapshot.
2. Enable/version an object-storage snapshot or copy the legacy bucket.
3. Record object counts and total bytes under `ecoaudit/`, `solarsense/`, and
   `installhub/`.
4. Confirm migrations `0012_installhub_cloud_backup.sql` and
   `0013_installhub_backup_access.sql` are present in the release artifact and
   migration journal.
5. Run `npm run verify` in the exact release commit.

### 1. Deploy compatibility code

Deploy with:

```dotenv
STORAGE_WRITE_MODE=legacy
ALLOW_LEGACY_UNSIGNED_UPLOADS=false
ALLOW_LEGACY_PUBLIC_FILES=true
ALLOW_LOCAL_BOOTSTRAP=false
ALLOW_LEGACY_BOOTSTRAP_UPSERT=false
ALLOW_LEGACY_SHARED_REGISTRATION_SECRET=false
```

`ALLOW_LEGACY_PUBLIC_FILES=true` is only a mixed-mobile-version bridge. Signed
upload URLs require no mobile change because the API returns the complete URL.
Monitor 401/403/404 rates and verify upload size/checksum failures still reject
the session.

### 2. Release authenticated clients

Release all three mobile apps and the portal with authenticated thumbnail and
original-image reads. Eco Audit and Solar Sense full-resolution local-PDF
fallbacks must send a bearer token; InstallHub thumbnails already do so.

After the supported-version threshold is reached, set:

```dotenv
ALLOW_LEGACY_PUBLIC_FILES=false
ALLOW_LEGACY_UNSIGNED_UPLOADS=false
```

Verify an unsigned `/v1/files/*` request and an unsigned raw upload both return
401, while an authorized owner/assignee request succeeds.

### 3. Start dual writes

Create the three isolated destinations and apply least-privilege IAM policies.
Use four distinct access-key identities during dual-write migration: one for
legacy storage and one scoped to each app bucket. Set `STORAGE_WRITE_MODE=dual`
and restart the API. New writes go to both the isolated app destination and
legacy storage. Reads prefer isolated storage and fall back to legacy.
Exact-content retries are idempotent, which makes a partial dual write safely
retryable.

### 4. Inventory and backfill

The command is a dry run unless `--apply` is supplied:

```bash
npm run storage:isolation-backfill -- --app=all
npm run storage:isolation-backfill -- --app=ecoaudit --apply
npm run storage:isolation-backfill -- --app=solarsense --apply
npm run storage:isolation-backfill -- --app=installhub --apply
```

Useful controls:

```text
--direction=legacy-to-isolated   default
--direction=isolated-to-legacy   rollback copy
--limit=N                        bounded batch per app
--overwrite                      replace only after a reviewed mismatch
```

Every applied copy verifies source and destination size and SHA-256. Existing
same-key data is accepted only when both match. A failed verification deletes
only the newly written destination copy and never the source. Save the JSON-line
output with the deployment evidence.

Repeat the dry run and applied batches until all source objects report
`already-present` or `copied` and no `missing-source`/verification errors remain.

### 5. Contract to isolated writes

Set `STORAGE_WRITE_MODE=isolated`. Reads still fall back to legacy, so rollback
remains available. Exercise each app independently:

1. back up a record with at least one original image;
2. render a server PDF and download it;
3. import a permitted copy and finish its thumbnail queue;
4. confirm a user from another app receives 404/403;
5. soft-remove the cloud copy and confirm its files are no longer authorized;
6. re-enable backup and confirm the same record ID is restored.

Keep legacy storage read-only for the agreed retention window. Its deletion is
a separate, explicitly approved operation and is not performed by this code.

## Cloud Backup opt-out and deletion

Turning backup off now asks the user to choose:

- **Keep Cloud Copy** — stop future uploads but retain the active server copy.
- **Remove Cloud Copy** — soft-delete the server tree and stop uploads.

Soft removal is intentionally reversible. Re-enabling backup upserts the same
local record ID and clears the server deletion marker. Eco Audit and Solar Sense
cache every referenced full-resolution original before removal; the operation
aborts if any original cannot be retained locally. InstallHub never deletes its
locally captured evidence after upload.

Previously opted-out Eco Audit/Solar Sense records expose a retained copy when
their existing `server_id` is present. InstallHub backfills
`cloud_backup_retained` from the existing per-installation sync watermark.

Permanent purge remains a separate, clearly destructive action in the remote
backup browser. It removes the server tree, unreferenced originals, report
artifacts, and versions. Storage/DB snapshots are the only recovery path after a
successful purge.

## Local-account migration and bootstrap shutdown

Normal Expo release bundles must not contain `EXPO_PUBLIC_REGISTRATION_SECRET`.
The mobile code ignores that value unless
`EXPO_PUBLIC_ENABLE_LEGACY_BOOTSTRAP=true` is also present.

If a one-off migration build is unavoidable:

1. set a different app-specific server secret;
2. enable `ALLOW_LOCAL_BOOTSTRAP=true`;
3. build only the intended app with both temporary Expo variables;
4. migrate inspector accounts with their real password;
5. verify that requested `admin` is ignored and new users are inspectors;
6. disable bootstrap, revoke/remove the app secret, and retire the build.

Passwordless bootstrap, account reactivation, email rebinding, and role
escalation are denied. `ALLOW_LEGACY_BOOTSTRAP_UPSERT=true` is a short rollback
bridge for already-created passwordless accounts; it preserves role, active
state, and email and must be disabled after remediation. Create/reset
administrators through the authenticated user-management flow or the controlled
server-side admin script.

## Rollback

- Application rollback: switch `isolated -> dual -> legacy`; reads already
  retain legacy fallback.
- Data rollback: run the backfill with
  `--direction=isolated-to-legacy --apply`. This is also copy-only and
  SHA-256-verified.
- Mixed old clients: temporarily set `ALLOW_LEGACY_PUBLIC_FILES=true`, with a
  dated incident/change record, then turn it off after client recovery.
- Never use a rollback flag to re-enable admin bootstrap.

## Production release gate

A deployment is not verified merely because local tests pass. The release
commit must contain the InstallHub schema, routes, migrations, migration-journal
entry, storage backfill command, and this runbook. Before production:

```bash
npm ci
npm run verify
npm run db:migrate
npm run storage:isolation-backfill -- --app=all
git status --short
```

The final command must be empty in the checked-out release artifact. Record the
database migration output, dry-run inventory, API health check, authenticated
file smoke test, and one complete backup/PDF/import smoke test per app.
